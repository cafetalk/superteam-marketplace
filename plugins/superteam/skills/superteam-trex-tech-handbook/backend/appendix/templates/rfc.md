# RFC 模板

> **何时用 RFC**：架构 / 跨服务 / 跨团队的重大设计变更；新引入中间件 / 框架；API 协议级修改。
> 小型功能 / 单服务内部重构不需要 RFC，写在 `<repo>/technical_design/` 目录即可。

---

# RFC: <标题>

**作者**：@<gitlab handle>
**日期**：<YYYY-MM-DD>
**状态**：Draft / Reviewing / Approved / Implemented / Abandoned
**Linear**：<TREX-xxx>

## 1. 背景

为什么要做这件事？解决什么问题？现状是什么？

## 2. 目标

可衡量的目标。不要"提升用户体验"这类模糊表述。

## 3. 非目标（Non-goals）

明确**不**在本 RFC 范围内的事项。

## 4. 方案设计

### 4.1 总览

- 一段话总结方案
- 必要时附架构图 / 时序图

### 4.2 接口 / 数据模型

- 新增 / 修改的 API
- 新增 / 修改的 DB 表 / OTS 表

### 4.3 实施步骤

- Phase 1: ...
- Phase 2: ...

## 5. 替代方案

- 方案 A：... → 优缺点
- 方案 B：... → 优缺点
- **采纳方案**：...（理由）

## 6. 影响面

- 兼容性（向前 / 向后）
- 性能影响
- 安全影响
- 运维影响

## 7. 风险与未决问题

- 风险 1：... → 缓解
- 未决：...

## 8. 时间线

- 设计完成：<日期>
- 实现 Phase 1：<日期>
- 上线灰度：<日期>
- 全量：<日期>

## 9. 评审记录

- <YYYY-MM-DD> @<reviewer>：approve / comment
